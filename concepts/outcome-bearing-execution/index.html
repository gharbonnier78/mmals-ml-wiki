Evidence governance

Outcome-bearing execution

An execution is outcome-bearing when its outputs can become scientific observations and can influence a claim, estimand, gate, belief, comparison, or scientific decision.

Research-method conceptreviewed 2026-08-24stable /go/ link

In plain language

If a run can teach you something about the scientific question, it is outcome-bearing. Loading a model, checking its file hash, or measuring memory use is usually not. Running the model on a benchmark and seeing its accuracy or FNMR is.

The practical rule is simple: if seeing the output could tempt you to change the protocol, threshold, model, hypothesis, or interpretation, treat the run as outcome-bearing before you execute it.

Engineering view

Non-outcome-bearing checks may establish that the execution machinery is safe and replayable without opening scientific evidence. Examples include syntax and CI checks, checkpoint SHA-256 verification, SBOM generation, deterministic smoke inference on synthetic inputs, throughput measurement, worker-count equivalence, and interruption/resume equivalence.

The boundary depends on what the output reveals. A throughput benchmark is engineering evidence; a benchmark accuracy is scientific evidence. A smoke test becomes outcome-bearing if it uses protected evaluation data or exposes a metric that can influence model or protocol choices.

Research view

Outcome-bearing is an epistemic property, not merely a label for the final experiment. Intermediate runs can be outcome-bearing if their observations can update beliefs, affect selection, alter stopping decisions, tune thresholds, or otherwise change the inferential path. This is why preregistration and explicit authorization must apply before such outputs are opened.

Separating outcome-bearing execution from engineering qualification helps prevent information leakage and researcher degrees of freedom: the infrastructure can be debugged without repeatedly peeking at the evidence that the frozen protocol is meant to judge.

Formal anchor

outcome-bearing ⇔ output can influence a scientific claim, estimand, gate, belief, comparison, selection, or decision
Governance boundary
Typical outcome-bearing examples

Accuracy, FNMR/FMR, TAR/FAR, ROC/DET, EER, loss curves used for scientific selection, ablation results, hypothesis tests, confidence intervals, or any intermediate result that can redirect the study.

Typical non-outcome-bearing examples

File hashes, licence/provenance checks, CI and lint, dependency audit, memory use, deterministic synthetic smoke tests, CPU throughput, restart/resume checks, and serial-versus-multiprocess digest equivalence—provided they do not reveal protected scientific outcomes.

Boundary

Non-outcome-bearing does not mean unimportant. It means the output is engineering or governance evidence rather than evidence about the scientific hypothesis.

Worked example

In a face-embedding qualification study, downloading AdaFace, verifying the exact checkpoint SHA-256, loading it, running a synthetic tensor through the frozen preprocessing/inference path, and measuring images/second are non-outcome-bearing engineering checks. Running the same frozen model on LFW, CFP-FP, CPLFW, CALFW or AgeDB-30 and comparing the resulting accuracy to a preregistered acceptance threshold is outcome-bearing.

Why this distinction matters

Without this boundary, a team can accidentally perform a sequence of “just sanity checks” that reveal enough scientific information to tune the study after seeing its evidence. The protocol may then look preregistered while the real decision path was already influenced by outcomes.
